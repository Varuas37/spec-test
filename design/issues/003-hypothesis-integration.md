# ISSUE-003: Hypothesis Property Testing Integration

## Summary
Integrate Hypothesis property-based testing to automatically generate thousands of test cases and find edge cases that manual tests miss.

## Motivation
Manual tests check specific examples, but property tests check properties across many inputs:

```python
# Manual: checks one case
def test_sort():
    assert sort([3, 1, 2]) == [1, 2, 3]

# Property: checks thousands of cases
@given(st.lists(st.integers()))
def test_sort_property(lst):
    result = sort(lst)
    assert len(result) == len(lst)
    assert all(result[i] <= result[i+1] for i in range(len(result)-1))
```

Property tests find edge cases like:
- Empty lists
- Single elements
- Duplicate values
- Integer overflow
- Unicode edge cases

## Detailed Description

### Current implementation

Install `spec-test[hypothesis]`. Link a synchronous property to its spec ID, then
call the actual implementation from the property. Use native Hypothesis
strategies and settings when a type annotation alone is not specific enough.

```python
from hypothesis import strategies as st
from spec_test import property_test

@property_test(
    "SORT-001",
    "Sorting preserves length and order",
    strategies={"items": st.lists(st.integers())},
    settings={"max_examples": 100},
)
def test_sort_property(items):
    result = sort(items)
    assert len(result) == len(items)
    assert all(a <= b for a, b in zip(result, result[1:]))
```

Initial inference covers `int`, `bool`, finite `float`, `str`, and `bytes`. Explicit
strategies take precedence, so a list or other domain type can be generated by
passing a strategy for that parameter. Use strategies to generate values inside
a runtime contract's intended domain. A contract error is a normal Hypothesis
test failure, not an implicitly discarded example. Native shrinking, example
database reuse, and explicit replay via Hypothesis decorators still apply. Keep
Hypothesis replay decorators such as `@example` outside `@property_test`.

This scope deliberately does not infer arbitrary types, handle async tests,
read a project-level Hypothesis configuration, or implement custom statistics
or CLI selectors from the original spec. Native Hypothesis settings, profiles,
and pytest reporting remain the configuration and diagnosis points.

## Options Considered

### Option A: Built-in property testing
**Pros**: No external dependency
**Cons**: Reinventing the wheel, Hypothesis is battle-tested

### Option B: Hypothesis integration (chosen)
**Pros**: Industry standard, powerful shrinking, database
**Cons**: Additional dependency

### Option C: QuickCheck-style custom
**Pros**: Full control
**Cons**: Significant implementation effort

## Decision
**Option B**: Hypothesis is the gold standard for property testing in Python. Integration is better than reimplementation.
